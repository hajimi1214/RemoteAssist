# Research notebook: responsive game streaming

The goal is reliable interactive play on an owner's Windows gaming PC, with an Alibaba Cloud ECS instance for signaling and optional TURN relay. A healthy ICE session can carry media directly between the clients; the cloud server only carries media when the selected pair uses a relay. Neither the server region nor a quality preset guarantees smooth play. Prove the path, the two clients' media budgets, and the input-to-display result separately.

## What to implement and measure first

- Keep direct UDP as the first path; use authenticated TURN over UDP when direct ICE fails. Label direct versus relay from the selected pair. For relays, distinguish the client-to-TURN transport from the candidate's media-side protocol: use `relayProtocol` where exposed, and say unknown where it is not. A relay advertised with a UDP media candidate does not prove that the allocation was reached over UDP.
- Start game qualification at 1080p60 on a real host and client. Use the encoder's queue and the actual receiver buffer to trade some detail for lower tail delay under load. Keep ordinary button/key transitions reliable and only coalesce transient movement; never let a backlog survive disconnect. Verify held input releases on blur, pause, timeout and teardown. Verify relative mouse behavior and multi-key input inside a game: UI click tests cannot substitute.
- Compare H.264, VP8 and any supported AV1 option on the same hardware only after verifying decode and encode costs; capability enumeration does not establish real performance. Retain browser congestion control, NACK and PLI handling. Higher resolutions and higher refresh rates compete for GPU, encoder, network and display time.
- Implement system audio as a separate measured milestone before calling the app a full game streamer. Capture Windows shared-mode loopback into an Opus/WebRTC audio track, keep its queue bounded, avoid file recording, and verify audio/video synchronization, mute, device changes and stop/restart on real Windows endpoints. Do not pass high-rate PCM through the UI thread.
- Keep neural enhancement out of the real-time path until it passes a separate test. A 60 fps stream schedules a new frame every 16.7 ms; models share that interval and GPU with game rendering and presentation. The prior CPU FSRCNN x2 experiment took 1064.75 ms median at 720p synthetic input and was not included in the runtime. That is evidence against this CPU configuration, not a benchmark of GPU inference. Compare a causal GPU prototype against normal scaling using identical decoded frames, resolution and bitrate. Record p95 GPU execution and added presentation delay, frame drops, scene-cut resets, text legibility and frame-to-frame shimmer on camera pans; retain the unenhanced path on misses.

## Acceptance on two real endpoints

1. Fix host and client versions, game/map and camera movement, refresh rates, codec, target resolution/FPS, and stream settings. Compare wired LAN, the actual home-to-client internet path and a controlled TURN-UDP run where the relay is deliberately selected and checked. Separately record results over Wi-Fi and TURN/TCP fallback if those are supported. Record unknowns explicitly; do not infer cross-network results from loopback.
2. Run a repeatable moving scene with visible keyboard/mouse reactions, five minutes per condition after warm-up; include a longer game run to detect drift or heat-related throttling. Record session path, median and p95 RTT, sender queue, average encode/decode and buffer dwell, prior/current decoded and presented frame counters where available, interval drops and freezes, and measured bitrate. The sample buffer dwell is `1000 * delta(jitterBufferDelay) / delta(jitterBufferEmittedCount)` in milliseconds, with no value for zero emissions or a counter reset. Decoder averages likewise use interval counters. Do not add counters to infer input-to-photon.
3. Use an external high-speed camera or hardware click-to-light sensor that can observe both the input trigger and the client display on the same timebase. A test page or game scene must have a repeatable, unambiguous local visual transition in response to that input. Measure dozens of samples per route; record p50/p95 and the measurement resolution. At 240 fps, video samples are about 4.17 ms apart; state that timing granularity. Follow with ordinary gameplay to check camera turns, rapid taps, held keys and disconnect behavior.
4. Size ECS bandwidth from the **observed relayed** bitrate and concurrency, and place the relay to minimize the combined paths of both endpoints. For scale, 10 Mbps sustained for one hour is about 4.5 GB of outbound video for one relayed viewer before overhead; direct traffic does not consume relay bandwidth. Consider overload beginning with packet loss and the high percentile of delay, not a speed-test maximum.

Current evidence in this notebook is reference review and the existing offline synthetic benchmark. No Alibaba Cloud deployment, sustained 1080p60 or 4K60 gameplay, physical gamepad pass, or cross-WAN input-to-photon measurement is established by the references. Record those results separately with the tested devices, routes and conditions.
