# Public Server Deployment

## Environment Variables

Use `deploy/.env.example` as the template. Replace `PUBLIC_DOMAIN`, `PUBLIC_BASE_URL`, `POSTGRES_PASSWORD`, `DATABASE_URL`, `JWT_SECRET`, `REFRESH_TOKEN_SECRET`, `TURN_REALM`, `TURN_EXTERNAL_IP`, and `TURN_SECRET` before deployment. Use unique random values of at least 32 characters for all token-signing and TURN secrets. Keep `TRUSTED_PROXY_CIDRS` limited to the private network ranges used by your reverse proxy, and keep `APP_ORIGINS` limited to the installed desktop app origins.

The deployment checker reads `deploy/.env`, refuses template values, and runs Compose validation without printing resolved secrets:

```powershell
.\scripts\verify-deploy-config.ps1
```

## Domain and TLS

The signaling container runs as an unprivileged user with a read-only root filesystem, no Linux capabilities, and no privilege escalation. Its temporary directory is an in-memory 64 MiB mount; it has a 512 MiB memory limit and a 128-process limit. These are single-instance starting limits. Monitor resource use during concurrent sign-ins and sessions before raising concurrency or changing the limits.

The Compose services and signaling Dockerfile base images are pinned to multi-platform OCI index digests. This makes a deployment reproducible across tag movement while selecting the matching platform manifest. To upgrade an upstream image, deliberately change both its reviewed tag and digest, refresh the component inventory, and regenerate/review its SBOM before deployment. Verify the resulting Compose configuration before applying it.

The production Compose topology terminates public HTTPS at Caddy. Go signaling listens on port 8080 inside the Compose network and is not published directly. Do not mount a development LAN certificate into the public deployment by setting `TLS_CERT_FILE` or `TLS_KEY_FILE` unless you also redesign and review the Caddy-to-signaling transport. For a standalone trusted-LAN test only, `scripts/dev-lan.ps1` can start the Go listener with an IP-SAN certificate and matching `PUBLIC_BASE_URL`; follow the certificate creation, per-user trust, key protection, fingerprint verification and trust-removal steps in the [LAN two-PC runbook](lan-two-pc-runbook.md). This direct LAN mode is separate from the production Caddy deployment.

Point the domain A/AAAA record to the server. Caddy listens on TCP `80` and `443` and obtains TLS certificates automatically.

## Ports

- TCP `80`: HTTP ACME challenge and redirect.
- TCP `443`: HTTPS and WebSocket signaling.
- TCP/UDP `3478`: TURN.
- UDP `49152-49200`: TURN relay range by default.

The ICE configuration endpoint requires a valid access token. `STUN_URLS` is optional and empty by default, so clients do not contact a public STUN provider unless the server operator explicitly configures one. Without STUN, peers can still use local candidates on a shared LAN. TURN uses short-lived REST credentials generated by the signaling service and validated by Coturn through the shared `TURN_SECRET`. Only plain TURN over UDP/TCP 3478 is configured; TURN-over-TLS is not enabled until a certificate is supplied and verified.

## Start

```powershell
Copy-Item deploy/.env.example deploy/.env
notepad deploy/.env
./scripts/verify-deploy-config.ps1
docker compose --env-file deploy/.env -f deploy/docker-compose.yml up -d --wait postgres
docker compose --env-file deploy/.env -f deploy/docker-compose.yml build signaling
docker compose --env-file deploy/.env -f deploy/docker-compose.yml run --rm --no-deps --entrypoint /signaling-migrate signaling
docker compose --env-file deploy/.env -f deploy/docker-compose.yml up -d --no-build
```

## Stop

```powershell
docker compose --env-file deploy/.env -f deploy/docker-compose.yml down
```

## Upgrade

Back up PostgreSQL before upgrading. The dump contains account, device and audit metadata. Store it in an access-restricted encrypted backup location. Review new or changed keys in `deploy/.env.example`; the deployment environment has no key migration, so preserve local secrets and update required settings deliberately. Signaling migrations are embedded, run in sorted filename order and commit together in one PostgreSQL transaction. There are no automatic down-migrations.

```powershell
.\scripts\backup-postgres.ps1 -Output .\.local\remoteassist-pre-upgrade.sql
$previousImageId = docker compose --env-file deploy/.env -f deploy/docker-compose.yml images -q signaling | Select-Object -First 1
if (!$previousImageId) { throw "No current signaling image was found to retain for rollback." }
docker tag $previousImageId remoteassist-signaling:previous
notepad deploy/.env
```

Set `REMOTEASSIST_VERSION` to the new version in `deploy/.env`, add any required environment keys, then validate the effective configuration. Keep a single signaling replica because active sessions are held in memory. Stopping signaling during an upgrade ends active sessions. Update both clients when the signaling or input protocol changes.

```powershell
.\scripts\verify-deploy-config.ps1
docker compose --env-file deploy/.env -f deploy/docker-compose.yml build signaling
docker compose --env-file deploy/.env -f deploy/docker-compose.yml up -d --wait postgres
docker compose --env-file deploy/.env -f deploy/docker-compose.yml stop signaling
docker compose --env-file deploy/.env -f deploy/docker-compose.yml run --rm --no-deps --entrypoint /signaling-migrate signaling
docker compose --env-file deploy/.env -f deploy/docker-compose.yml up -d --no-build
```

A previous image is usable only when its schema and protocol remain compatible with the already-applied migrations.

`SESSION_ACTIVE_TTL` defaults to 8 hours from session creation (supported range 1 minute to 8 hours). This is separate from the five-minute legacy invitation code. Same-account direct sessions do not require that code. Both the server and Windows input gate enforce the active deadline.

## Rollback

If the previous image is compatible with the applied database schema, set `REMOTEASSIST_VERSION=previous` in `deploy/.env`, verify the effective config, then recreate only the signaling service:

```powershell
notepad deploy/.env
.\scripts\verify-deploy-config.ps1
docker compose --env-file deploy/.env -f deploy/docker-compose.yml up -d --no-build --no-deps signaling
```

This does not reverse database migrations. If the older image cannot use the new schema, create a separate empty compatible database, restore the pre-upgrade dump there with `-DatabaseName`, then set both `DATABASE_URL` and `POSTGRES_DB` to that existing recovery database. `POSTGRES_DB` on an initialized volume does not create a database. Verify the effective config before recreating the older signaling service. Keep the previous database intact until rollback is accepted.

## Backup

```powershell
.\scripts\backup-postgres.ps1 -Output remoteassist-backup.sql
```

The backup script checks that the host, database, user and password in `DATABASE_URL` match the Compose PostgreSQL settings, then dumps that database. It commits the destination file only after validating successful plain-SQL output. Restrict access to the backup and store it encrypted. It contains account, device, token-hash and audit metadata.

## Restore

Stop signaling and restore into an empty target database. The restore script uses `ON_ERROR_STOP` and a single transaction. It does not drop an existing database. Any SQL failure rolls the restore back. For a rollback, create a separate empty database, restore into it with `-DatabaseName`, then change both `DATABASE_URL` and `POSTGRES_DB`, verify configuration, and recreate signaling. Keep the previous database available until the recovered service has been accepted.

```powershell
.\scripts\restore-postgres.ps1 -Input remoteassist-backup.sql
```

For an isolated recovery database, stop signaling, create an empty database and provide its name explicitly:

```powershell
docker compose --env-file deploy/.env -f deploy/docker-compose.yml exec -T postgres sh -c 'export PGPASSWORD="$POSTGRES_PASSWORD"; exec createdb --no-password --username="$POSTGRES_USER" remoteassist_restore'
.\scripts\restore-postgres.ps1 -Input remoteassist-backup.sql -DatabaseName remoteassist_restore
```

After validating the restored data, set both `DATABASE_URL` and `POSTGRES_DB` to `remoteassist_restore`, run `scripts/verify-deploy-config.ps1`, and recreate the signaling service. `POSTGRES_DB` only initializes a new PostgreSQL data volume and changing it does not create this database; the `createdb` command above does that explicitly. Keep the previous database intact until recovery is accepted.

## P2P and TURN Fallback Verification

1. Test two clients on a permissive LAN and confirm the UI shows `P2P`.
2. Test clients behind restrictive NAT or block direct UDP between them and confirm the UI shows `TURN Relay`.
3. Confirm no screen content, keyboard content, token, or TURN secret appears in logs.

Firewall rules, cloud security groups, DNS, TLS, and real server deployment are manual steps and are NOT VERIFIED in this workspace.
