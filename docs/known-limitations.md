# Known Limitations

- Windows 10/11 is the first supported desktop target.
- macOS and Linux desktop behavior is NOT VERIFIED.
- Installing the NSIS package on another Windows 10/11 PC is NOT VERIFIED.
- The 0.9 tablet LAN test displayed the Windows desktop but reported touch/quality issues. The 0.12 UI and media paths have synthetic browser coverage; physical 0.12 tablet revalidation is pending.
- Public server deployment, DNS, TLS issuance, firewall rules, and TURN relay behavior are NOT VERIFIED without real infrastructure.
- The standalone Go signaling service now has optional TLS certificate loading with HTTPS-root, leaf validity, SAN, CA/basic-constraints and server-auth EKU checks. Certificate generation includes a private-IP SAN, short validity, Windows key-file ACLs, and root-store removal instructions. Python generation and Go TLS handshake/configuration tests pass. Windows CurrentUser root-store behavior in the packaged Tauri/WebView2 client and an actual two-PC LAN HTTPS/WebRTC session are still NOT VERIFIED.
- Go migration runner applied and reran migrations 001–003 against a temporary PostgreSQL 18.2 Windows server bound to loopback. Duplicate preflight and rollback were tested. Production and Compose database instances remain UNVERIFIED.
- PostgreSQL backup/restore scripts validate local files and restore in one transaction. Runtime backup and restore against a Compose PostgreSQL service remain NOT VERIFIED on this host because Docker Engine is unavailable.
- Bounded Unicode text and common navigation keys are supported; vendor mobile IME and scan-code-specific shortcuts still require real-device validation.
- Multi-monitor absolute coordinate mapping is normalized to the primary desktop coordinate range and needs manual DPI validation.
- Active sessions remain in memory; use one signaling replica. Restart ends active sessions.
- The current Windows stream reads D3D11 staging data to CPU memory, copies frames through Tauri IPC, uploads them into WebGL, and uses browser-managed WebRTC encoding. No zero-copy D3D11-to-encoder path is implemented. Sustained 1440p60/4K60 and hardware encoding are NOT VERIFIED.
- DXGI acquire wait follows the capture FPS budget and is capped at 40 ms, but an idle desktop can still return an empty acquisition and bursty updates can still miss the requested frame schedule. No physical A/B latency result is available.
- The 2026-11-26 opt-in DXGI smoke failed before frame acquisition: preferred BGRA duplication returned `DXGI_ERROR_UNSUPPORTED (0x887A0004)`, then compatibility `DuplicateOutput` returned `E_ACCESSDENIED (0x80070005)`. A read-only `OpenInputDesktop` probe also returned Win32 access denied (5), confirming the command runner cannot inspect the interactive desktop. A user-launched client remains unverified.
- Capture diagnostics report bounded frame-pull windows, asynchronous WebGL upload/draw GPU timing when the disjoint timer extension is available, and browser-reported encoder/decoder implementation. P99/max are withheld below 100 timing samples. A standalone Chromium GPU timer smoke passed on the local RTX 4060, but packaged WebView2 extension availability and RemoteAssist GPU timing remain unverified. WebView presentation callbacks do not measure physical display scanout.
- Version 0.12 captures the primary display through DXGI. scRGB HDR is converted to SDR by a tested software tone mapper, but real HDR output/color fidelity and moving-4K conversion cost have not been measured. Rotated displays, secondary displays, mode changes and multi-monitor DPI/input still need validation.
- Adaptive encoding and dual DataChannels passed a local browser loopback; target WebView2 behavior, the 0.13 emergency downgrade on a real weak link, stable 4K60 and input-to-photon latency need real-device/two-machine measurement.
- Automatic encoding now starts at the Balanced tier, with a configured 20 Mbps ceiling for a 4K source, and upgrades only after measured headroom. This has not been A/B measured on the two Windows machines; actual FPS, encoder choice and input-to-display latency still require a live session.
- Native smoke on 2026-11-25 measured two 2560×1600 SDR scenes. The animated pattern emitted 120 packets, 1 full and 119 delta, with 82.8% fewer payload bytes than full-frame equivalents. An ambient desktop burst returned 3 pixel frames and 27 empty DXGI timeouts. Details and timing windows are in `performance-baseline.md`. Neither sample measures WebRTC sustained output.
- Capture diagnostics carry bounded pull counts, empty responses, failed pulls and full/delta/dirty-region counts over authenticated heartbeat. WebView `requestVideoFrameCallback` cadence and optional asynchronous GPU command execution timing are reported when supported. These do not measure physical display scanout. System/game audio and WASAPI loopback are not implemented.
- Version 0.15 streams video only; Windows system/game audio capture, Opus transport and receiver audio playback are not implemented. It is not yet a complete game-streaming replacement.
- The game camera path captures browser-relative pointer movement and injects standard Windows SendInput events. It is not a physical HID/Raw Input device, does not guarantee edge-free camera motion, and may be ignored by games or anti-cheat software. Qualification is per title; do not bypass game security controls.
