# Two-Windows LAN Acceptance Runbook

## Purpose and scope

Use this runbook with two Windows 10/11 PCs on the same trusted private LAN. It exercises both product flows:

- **My Devices** for two devices under one account, with no one-time code.
- **Remote Assist** for two different authenticated users, with a one-time eight-digit code generated by the host.

The local signaling service stores users, devices and sessions in memory. Stopping it ends the test and removes that test data. The LAN debug installer accepts HTTP only for RFC1918 IPv4 addresses and is not a public-deployment client.

## Record the current LAN addresses

On the Windows PC that will host the test service, run:

```powershell
Get-NetIPAddress -AddressFamily IPv4 |
  Where-Object {$_.IPAddress -match '^(10\.|192\.168\.|172\.(1[6-9]|2[0-9]|3[0-1])\.)'} |
  Select-Object InterfaceAlias,IPAddress,PrefixLength
```

On the second PC, run `ipconfig`. Confirm both addresses are on the same subnet and neither is a guest Wi-Fi client. Do not reuse the earlier `192.168.0.100` address if it is no longer assigned to the host.

Set the actual host address in a local PowerShell variable, for example:

```powershell
$LanHostAddress = "10.250.218.84"
```

## Start an isolated local signaling service

From the repository on the host PC:

```powershell
.\scripts\dev-lan.ps1 -Address $LanHostAddress -Port 8080
```

Keep this foreground window open. It uses a fresh in-memory store and binds only to the selected LAN interface. The service URL is `http://<host-address>:8080`.

In a second terminal on the host PC, build the Windows LAN test installer and copy it into the ignored download directory:

```powershell
.\scripts\package-windows-lan.ps1 -Address $LanHostAddress -Port 8080
```

Then serve only that download directory:

```powershell
python -m http.server 8090 --bind $LanHostAddress --directory .\.local\lan-test-download
```

The download URL is:

```text
http://<host-address>:8090/RemoteAssist_0.15.1-alpha_x64-setup.exe
```

If Windows Firewall asks, allow the foreground Go signaling process and Python download server on the trusted **Private** network only. Do not disable the firewall or create a router port-forward.

## Install and confirm service reachability

On both PCs, download the installer from the host and install it interactively. The LAN package embeds the selected host service URL. If a different saved service URL is present, use Settings → Connection service to set `http://<host-address>:8080`.

On the second PC:

```powershell
Test-NetConnection <host-address> -Port 8080
Test-NetConnection <host-address> -Port 8090
```

On the host, verify `http://127.0.0.1:8080/healthz` returns status `ok`. A working `/healthz` or TCP port does not establish WebRTC media connectivity.

## Flow A — same-account devices

1. Sign in to the same disposable test account on both PCs.
2. Keep the Windows host client visible and signed in.
3. On the controller, open **My Devices** and click the online Windows host once. The desktop should enter full-window control directly.
4. Confirm the desktop appears without a code-entry, screenshot-picker or per-session approval dialog. If a Windows/runtime prompt appears, record its title and publisher so the prompt source can be identified.
5. Confirm the host shows who is connected and that its visible pause/stop action ends control.
6. Move the mouse, click, use the wheel, press/release keys, and send bounded text.
7. Disconnect from the floating control. Confirm the host releases held keys and mouse buttons.

## Flow B — one-time Remote Assist code

1. On the host, sign in to a disposable account. On the controller, sign in to a different account.
2. On the host, open **Remote Assist** and generate a code. Tell the code to the controller through your chosen private channel.
3. On the controller, open **Remote Assist**, enter all eight digits and select Connect.
4. Confirm the host begins the visible session without a second authorization dialog. The entered code is single-use and expires after five minutes.
5. Repeat the same mouse, keyboard, text, stop and release checks as Flow A.
6. Try an invalid, expired, and already-used code. Each must fail closed and leave capture/input inactive.

## Measurements

For each flow, record client/host model and GPU, Windows version, app build, display resolution/refresh, selected route, and the following:

| Measurement | Evidence source |
|---|---|
| First-frame time | Stopwatch from Connect to first moving frame |
| Actual receive FPS | Connection diagnostics. Decoded FPS and WebView frame-presentation callbacks are reported separately |
| Codec / implementation | WebRTC statistics when the installed WebView exposes them; mark unavailable otherwise |
| RTT, loss, jitter, bitrate, sender queue | Interval WebRTC stats |
| Capture reply P50/P95/P99/max and full/delta/empty/failure counts | Authenticated heartbeat capture diagnostics |
| Presentation callback FPS and interval percentiles | `requestVideoFrameCallback`, where supported. This is not physical panel scanout |
| Input-to-display p50/p95 | External high-speed recording or a click-to-light sensor with repeatable visible response |
| CPU, GPU, memory | Windows Task Manager or Performance Monitor; record before/after idle and active session |

Run a 5-minute moving pattern first, then a 30-minute desktop/game session. Repeat under idle desktop, scroll/text, and high-motion content. Never infer input-to-display from RTT.

## Disconnect and failure checks

- Pause/stop on the host and close the controller independently.
- Unplug/reconnect one network interface or disable/enable Wi-Fi only if this is safe for the test PC. Confirm the session ends fail-closed and held inputs are released.
- Revoke a device or let the session expire. Confirm input stops and old-session packets cannot affect a newly started session.
- If the route changes or the WebSocket drops, record whether the client reports an ended session. Automatic ICE restart/reconnect is not implemented.
